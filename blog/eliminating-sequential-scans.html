Why Sequential Scans Kill Database Performance

When a PostgreSQL table grows to millions of rows, executing a query without a matching index forces the query planner to perform a Seq Scan (Sequential Scan). This means reading every page on disk from start to finish, thrashing Shared Buffers and spiking CPU utilization to 100%.

1. Analyzing the EXPLAIN ANALYZE Execution Plan

Before adding indexes, always run EXPLAIN (ANALYZE, BUFFERS). Look for the Seq Scan on table_name node. Take note of the total cost and actual time spent reading disk pages.

2. B-Tree Composite Index Ordering Rule

When creating multi-column indexes, place equality predicates (status = 'ACTIVE') FIRST in the index definition, followed by range predicates (created_at >= '2026-01-01').

3. Partial Indexes for High-Cardinality Filtering

If 95% of your table rows have status = 'PROCESSED' and you only query status = 'PENDING', build a Partial Index: 

CREATE INDEX idx_pending_jobs ON queue_jobs (created_at) WHERE status = 'PENDING';
